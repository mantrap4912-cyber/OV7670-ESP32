# Clocks, timing and memory bandwidth

Everything in a non-FIFO capture is a consequence of one number: how fast bytes
leave the sensor. This page explains what sets that number and what it costs you.

## The clock chain

```
LEDC (APB 80 MHz / N)  ->  XCLK  ->  [OV7670 internal divider: CLKRC]  ->  PCLK
```

1. **XCLK** is generated by an LEDC timer at 1-bit resolution, giving an exact
   50% square wave. The OV7670 accepts 10–48 MHz; this library allows 1–40 MHz
   and defaults to 16 MHz, which is a good compromise between frame rate and
   signal integrity on jumper wires.

   LEDC divides APB by an integer, so the delivered frequency is often a little
   off the request. `xclk_actual_freq()` reports what you actually got, and the
   library warns if the error exceeds 5%.

2. **CLKRC (register 0x11)** divides XCLK inside the sensor. Bits [5:0] hold a
   prescaler; `cfg.clkrc_prescaler` writes it directly.

   - `0` — no division, fastest PCLK, highest frame rate, least timing margin.
   - `1` — the library default. Roughly halves PCLK. Noticeably more tolerant of
     long or unshielded wiring, at the cost of frame rate.
   - Higher values trade more frame rate for more margin.

   This is the single most useful knob when capture is unreliable. If raising it
   fixes your image, the underlying problem is electrical, not software.

3. **PCLK** clocks one byte out of the sensor per edge. It is what the I2S
   peripheral samples on, and it is the timing-critical signal on the board.

## What the capture peripheral has to keep up with

At 2 bytes per pixel, one line of an *N*-pixel-wide frame is 2*N* bytes on the
bus. The I2S FIFO in the sampling mode used here pads every sample with a byte,
so the DMA buffer for that line is **4*N* bytes** — twice the line length. The
unpack step in the capture task squeezes the padding back out.

| Frame size | Bus bytes/line | DMA bytes/line | Lines/frame |
|---|---|---|---|
| QQVGA | 320 | 640 | 120 |
| QCIF | 352 | 704 | 144 |
| QVGA | 640 | 1280 | 240 |
| CIF | 704 | 1408 | 288 |
| VGA | 1280 | 2560 | 480 |

A single DMA descriptor can describe at most 4092 bytes, which is why one line
per descriptor works for every supported resolution — VGA's 2560 is the largest
and still fits comfortably.

## Interrupt and task load

One DMA completion interrupt fires per line. At VGA and 15 fps that is
480 × 15 ≈ **7200 interrupts per second**, each followed by a task wakeup that
unpacks 2560 DMA bytes into 1280 stored bytes.

That is why the unpack happens in a high-priority task rather than in the ISR:

- The ISR stays short enough to be safely flagged `IRAM_ATTR`.
- The frame buffer may live in PSRAM. An interrupt registered with
  `ESP_INTR_FLAG_IRAM` can run while the flash/PSRAM cache is disabled, and must
  never dereference cached memory — so the copy cannot happen there.

## The DMA ring and why depth matters

`cfg.dma_node_count` sets how many line-sized buffers the ring holds. The DMA
engine writes into them in rotation; the task drains them behind it. The gap
between the two is your entire timing margin.

With the default of 4 nodes, the task may fall up to **three line periods**
behind before the engine catches up and overwrites data that has not been read.
At QVGA that is on the order of a couple of hundred microseconds — comfortable
for a task at priority `configMAX_PRIORITIES - 2`, but not infinite.

Raise `dma_node_count` when:

- You see `frames_torn` or `dma_overruns` climbing in `getStats()`.
- You are doing real work in a line callback (pushing to a TFT over SPI, for
  instance) — 8 or 16 is sensible there.
- You are running at VGA, where each line is 2.5 kB and the unpack takes longer.

The cost is internal DMA-capable RAM: `node_count × 4 × width` bytes. Even 16
nodes at VGA is only 40 kB.

## Frame rate expectations

The OV7670 at 24 MHz XCLK with no internal division nominally produces 30 fps at
VGA. In practice, on this capture path, expect rather less — the limit is usually
how fast the CPU can drain and unpack, or what you do with the frames afterwards.

Realistic starting points at 16 MHz XCLK with `clkrc_prescaler = 1`:

- QQVGA: comfortably above 20 fps
- QVGA: mid-teens
- VGA: single digits, and only via a line callback on a board without PSRAM

Run `05_ContinuousBenchmark` for the real numbers on your board and wiring; the
spread between a clean short-wire setup and a long ribbon is large.

## Memory bandwidth, honestly

Moving frames is usually more expensive than capturing them:

- A VGA RGB565 frame is 614 kB. Over WiFi at a realistic 2–3 MB/s that is roughly
  4 frames per second before anything else happens.
- A QQVGA frame is 38 kB, which is why the streaming examples default to it.
- Converting RGB565 to 24-bit BMP for a browser inflates the frame by 50%.

If you need real video over a network, the honest answer is that the OV7670 is the
wrong sensor — it has no hardware JPEG encoder, and software JPEG on an ESP32 will
cost you more than the capture does. Sensors like the OV2640 encode on-chip. This
library is at its best feeding a local display, doing on-device image processing,
or serving stills.
